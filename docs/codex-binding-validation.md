# Codex 绑定可行性验证

验证日期：2026-10-22。宿主：Windows，`codex-cli 0.163.0-alpha.11`。

## 可用能力与边界

| 场景 | 本次证据 | 产品状态 |
| --- | --- | --- |
| 无启动绑定，跟随全局空间 | Core 与真实 stdio MCP 回归 | 已实现 |
| `--workspace-id` 固定范围 | 三个同时运行的 stdio 进程；损坏/失效绑定报错 | 已实现 |
| 受信任项目覆盖用户 MCP 参数 | 隔离 Codex 的 `mcp get --json`，以及真实宿主 MCP 调用 | 已验证 |
| CLI `-c` 覆盖项目 MCP 参数 | 隔离 Codex 的实际配置解析 | 手动途径；使用时仍需 `context` 核验 |
| `SessionStart` / `PreToolUse` 注入会话标识 | 隔离 Hook 配置已启用，但未观察到事件记录或注入参数 | 未验证，不启用自动绑定 |
| MCP 请求元数据 | 实际 CLI 请求中观察到会话相关 `_meta` 字段 | 仅观察；未作为产品依赖 |
| 桌面并发任务、共享 MCP 连接、恢复会话 | 本次未完成真实桌面调用矩阵 | 未验证，不承诺任务自动隔离 |

探针 `scripts/codex-binding-probe.mjs` 创建一次性目录，配置合成 MCP 和本机 Responses 端点，由真实 Codex CLI 执行工具调用。测试端点仅返回预设工具调用及结束消息，不使用真实模型或账号凭据。项目仅覆盖 `args`，验证继承全局 `command`；命令行再覆盖完整 `args`。真实 MCP 收到的合成范围为 `project-a`。

Hook 探针只记录事件名称和合成会话标识，并尝试通过 `updatedInput` 注入 `session_id`。一次性信任开关仅用于脚本创建并审查的临时测试 Hook，不修改日常配置。本次没有观察到该链路工作，不能从文档所列事件推断当前 CLI 路径、桌面与恢复路径均可用。

真实请求的 `_meta` 出现 `callId`、`x-codex-turn-metadata`、`threadId`、`sessionId`、`windowId`、`itemId`、`progressToken` 等键。键存在不等于它们具有跨运行方式、恢复会话和多任务共享连接所需的稳定语义。产品没有读这些字段建立任务映射，也没有提供看似可用的自动任务列表。

## 官方资料与实际验证的区别

[配置优先级](https://learn.chatgpt.com/docs/config-file/config-basic)说明受信任项目配置和 CLI 覆盖的层级；本次另外通过真实 CLI 解析和调用进行了核对。

[Hooks 文档](https://learn.chatgpt.com/docs/hooks)列出事件、会话标识、MCP 参数改写和信任要求，也说明部分 Hook 失败不会阻断工具调用。因此仅增加 Hook 不足以保证隔离；若以后实现自动会话绑定，还需要服务器端对缺失/失效身份采取明确错误策略，并验证并发、恢复和桌面路径。

## 后续启用自动绑定前所需证据

1. 在受控测试项目中分别记录 CLI、桌面、恢复与并发任务的真实请求身份；证明其稳定性和来源。
2. 在同一共享 MCP 连接上交错调用，证明每次请求都可可靠归属，不能使用“最后启动的会话”或进程全局变量代表调用者。
3. 验证身份缺失、Hook 被禁用/超时、绑定记录损坏和目标工作区删除时均不会回退到其他空间。
4. 通过 Desktop/受控本地服务创建、修改和移除映射，MCP 和资源文本不得修改绑定。

本次交付采用可验证的启动参数绑定；未来可在同一资源解析层加入经过验证的会话选择，不需要扩张三个只读查询工具。
