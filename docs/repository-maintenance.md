# 两个仓库的维护守则

## 定位与默认方向

- **开源仓库（本目录）**：公共产品代码、文档、测试、问题修复和发行来源。默认分支 main。
- **私有仓库**：内部规划、私人资源和尚未决定公开的实验。保留既有历史与分支，不因开源准备而改写。
- 两个仓库拥有独立历史。公共功能默认在开源仓库实现，私有版按需吸收。它们不必保持完全相同的代码或版本。

## 开始任何修改前

1. 确认当前目录、Git 根目录、分支及 remote，明确本次目标是开源版还是私有版。
2. 每次任务只默认修改一个仓库。跨仓库同步须明确说明来源、目标和文件范围。
3. 功能工作使用短分支，例如 codex/fix-notebook-save；完成检查后再合入相应主线。
4. 两边的依赖、构建目录、测试数据和用户数据保持独立。测试使用各自隔离数据，避免同时操作日常个人工作区。

## 公共功能与私有实验

公共功能、兼容性修复和普通文档改进直接在开源仓库开发。先在私有版探索的功能，
须完成代码、样例、许可与隐私审核后，作为新改动移植到开源版。
不得把私人路径、邮箱、令牌、日志、截图、真实工作区或内部讨论带入公开源码。

## 同步规则

| 方向 | 方法 | 不带入的内容 |
| --- | --- | --- |
| 开源 → 私有 | 记录公开源提交；选择性移植文件或补丁，检查私有定制冲突后形成私有提交 | 公共构建缓存、测试数据、node_modules |
| 私有 → 开源 | 先导出批准文件或不含提交元数据的代码 diff；在开源工作分支审阅并形成新提交 | 私有 Git 历史、提交说明、作者邮箱、分支与标签、内部报告及数据 |

不要直接合并两个仓库的历史，不使用 --allow-unrelated-histories，不 mirror 推送。
不在开源仓库配置指向私有仓库的 remote，不向其中 fetch 私有历史，也不直接 cherry-pick 私有提交。
涉及二进制或图片时，另外检查内容与元数据。不要复制整个目录覆盖另一仓库。

同步记录保存在私有的本地台账：日期、方向、公开提交（如有）、变更范围、验证结果和接收提交。
公开提交说明描述问题与修复，不写私有仓库地址、旧 SHA 或内部讨论。
同步不是自动化任务；一次同步授权不代表以后可持续同步或推送。

## Git 身份、提交与远端

- 开源仓库使用本地配置的公开维护名和 GitHub noreply 邮箱，不修改全局身份。
- 提交前检查 git status、git diff --cached 和暂存文件清单；忽略规则不能替代检查。
- 只有明确目标仓库与远端后才推送；本地提交、上传、公开可见性、发布版本是独立动作。
- 开源仓库的 origin 仅指向指定的 macydog-m/Dockyard 仓库（准备阶段保持私有），不能沿用私有 origin。
- 不默认强推、改写已共享历史或删除远端分支。

## 版本、验证与发布

公共发行只从开源仓库的审核提交构建。根 package.json 是版本来源，使用 version:set
同步工作区与锁文件。私有版记录它基于哪个公开版本；若分发不同内容，使用明确的内部版本标识，
不把不同二进制冒充同一个公开版本。

根据变更执行相关测试。发布前执行 npm ci、npm test、npm run desktop:build、
npm run privacy:check、npm audit，并检查图标与依赖许可。需要桌面行为验证时运行隔离烟测。
依赖告警以每次发布前的实际审计结果为准，不能因为构建通过就视为已解决。

首次正式分发前，另行验证干净 Windows 安装、升级、卸载保留数据和真实宿主连接。
构建产物、校验和与更新说明必须对应同一审核版本；源码审阅 ZIP 不作为安装器发行。
不把私有版旧包上传到公共 Release。

## 常用约定

- “改公共功能”默认在开源仓库；“内部实验”默认在私有仓库。
- “同步”必须说明方向与范围；“上传”必须明确目标仓库与分支。
- 本守则不授权新建远端、自动同步、上传、公开或发布。
